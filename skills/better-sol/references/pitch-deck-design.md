# Pitch Deck Design

Use this reference when the user asks for a pitch deck, investor deck, grant deck, demo-day slides, or wants slides to look credible.

## Deck principles

- One idea per slide.
- Slide title should state the conclusion, not the topic.
- Use proof over adjectives.
- Show the product early.
- Do not overload technical architecture slides.
- Make Solana relevance obvious but not performative.
- Use consistent visual rhythm: title, one visual, one takeaway.

## Slide sequence

A strong crypto deck usually uses:

1. Title: product, tagline, category.
2. Problem: specific user pain.
3. Existing workaround: why current solutions fail.
4. Solution: what the product does.
5. Demo/product: screenshots or flow.
6. Why now: market, infrastructure, regulation, user behavior, protocol maturity.
7. Why Solana: speed, cost, composability, liquidity, mobile, payments, developer ecosystem.
8. Technical architecture: program, client, protocols, data flows.
9. Traction or validation: users, waitlist, pilots, transactions, tests, integrations.
10. Business or growth model: distribution and monetization.
11. Competitive wedge: why this wins.
12. Roadmap and ask.

## Visual system

Pick one direction:

### Developer infrastructure

Dense but clean. Monospace accents, diagrams, code snippets, terminal proof, restrained color.

### DeFi / financial

Dashboard screenshots, metric cards, risk labels, conservative palette, precise numbers.

### Consumer crypto

Large product screenshots, simple language, warmer palette, fewer acronyms.

### Hackathon demo

High proof density: screenshots, transaction signature, devnet program, test output, architecture diagram.

## Architecture slide

Show only what matters:

- user/wallet
- frontend/client
- Better Sol typed client
- Better Sol program or external program
- protocol integrations
- data/indexer/backend if present

Avoid drawing every package, file, and API.

## Better Sol slide angle

Use when the audience cares about technical implementation:

- TypeScript program definition is the source of truth.
- The same definition drives typed client calls.
- Tests run with LiteSVM.
- Deploy flow reaches devnet/mainnet.
- Less client drift than IDL/codegen-heavy workflows.

## Common deck mistakes

- Leading with technology before pain.
- Saying “decentralized” without explaining user benefit.
- Showing architecture before product.
- Using fake traction.
- No clear ask.
- Too many screenshots with no callouts.
- Text too small for a projected demo.

## Asset checklist

- logo or wordmark
- product screenshots
- transaction signature or explorer link
- architecture diagram
- traction/proof numbers
- team credibility
- roadmap milestones
- final CTA/contact
