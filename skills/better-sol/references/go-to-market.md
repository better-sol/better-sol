# Go-to-Market for Crypto Products

Use this reference when planning launch strategy, distribution channels, community building, and growth for a crypto product.

## Launch phases

### Pre-launch

- Define the core user and their specific pain.
- Build a waitlist or early access list.
- Create technical documentation and setup guides.
- Establish presence on relevant platforms: Twitter/X, Discord, GitHub.
- Ship to devnet with working demo.
- Gather early feedback from 5–20 users.

### Launch

- Deploy to mainnet with monitoring.
- Publish announcement with proof: transaction, demo, working product.
- Engage communities where target users are active.
- Submit to relevant directories, aggregators, and protocol integration lists.
- Line up initial content: blog post, technical walkthrough, social thread.

### Post-launch

- Monitor for failures, errors, and user confusion.
- Respond to feedback publicly and ship fixes quickly.
- Track key metrics: active wallets, transactions, retention.
- Iterate based on real usage data.
- Plan next feature or integration based on user requests.

## Distribution channels

### Developer adoption

- Documentation and examples that work on first try.
- GitHub presence with clear README and contribution guidelines.
- Integration guides for popular frameworks and tools.
- Developer grants and bounties.
- Conference talks, workshops, and hackathons.
- Developer tools directories.

### User adoption

- Product-led growth: the product sells itself through usage.
- Content marketing: tutorials, comparisons, and use case guides.
- Community building: Discord, Telegram, Twitter/X spaces.
- Referral programs with genuine incentives.
- Integration with existing user-facing products.
- Press coverage for significant milestones.

### Protocol integrations

- Build on top of established protocols for composability.
- List on protocol dashboards and aggregators.
- Co-market with integration partners.
- Contribute to protocol governance discussions.

## Community building

### Principles

- Community forms around shared interest, not just a token.
- Consistent public presence builds trust over time.
- Transparency about progress, setbacks, and decisions.
- Empower community members to contribute and lead.
- Quality over quantity: 100 engaged users > 10,000 airdrop farmers.

### Platforms

- Discord: real-time discussion, support, governance, contributor coordination.
- Twitter/X: announcements, thought leadership, engagement with the ecosystem.
- GitHub: code, issues, contributions, and technical credibility.
- Forums: long-form governance discussions and proposals.
- Blog: technical deep dives, product updates, and vision.

### Contribution models

- Open-source contributions with clear contribution guidelines.
- Bounty programs for specific tasks.
- Grant programs for ecosystem development.
- Ambassador programs for community leaders.
- Hackathons for experimental development.

## Growth metrics

### Technical metrics

- Transactions per day/week/month.
- Active wallets interacting with the program.
- Program deployment uptime.
- API/RPC reliability.
- Average transaction cost.
- Compute unit efficiency.

### Product metrics

- Daily/monthly active users.
- Retention: day-1, day-7, day-30.
- Conversion from visitor to first transaction.
- Time to first successful on-chain action.
- Support ticket volume and resolution time.

### Financial metrics

- Total value locked or transacted.
- Protocol revenue.
- Token price and liquidity depth.
- Cost per acquisition.
- Unit economics per transaction or user.

## Positioning for different audiences

### Developers

Lead with technical architecture, developer experience, and code quality. Show working examples and tests. Emphasize type safety, speed of iteration, and maintainability.

### End users

Lead with the problem solved and the experience of using the product. Avoid jargon. Show the product working, not the technology behind it.

### Investors and grant reviewers

Lead with market opportunity, team capability, and proof of progress. Show traction, validation, and a credible plan.

### Judges at hackathons

Lead with working demo, on-chain proof, and clear differentiation. Show the product running, not slides about it.

## Common launch mistakes

- Launching with marketing before the product works reliably.
- Targeting everyone instead of a specific user segment.
- Relying on a token launch to generate product interest.
- Ignoring post-launch monitoring and support.
- Overpromising features that are not built.
- Focusing on hype metrics (followers, airdrop signups) instead of usage metrics.
- Launching on mainnet without devnet testing and security review.
- Not having a plan for what happens after launch day.
