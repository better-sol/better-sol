# Concept — What We're Building

## What We're Building

**A TypeScript library + CLI that make Solana program development feel native to JavaScript developers.**

```
better-sol              →  Define programs + interact with them (runtime library)
@better-sol/cli         →  Create programs + compile + deploy (`create`, `deploy`, `verify`)
```

The same TypeScript file that defines the on-chain program is the typed client SDK. Zero extra code needed.

---

## The Complete Workflow — Start to Finish

### 1. Install

```bash
npm install better-sol
```

One package. That's it. No Rust toolchain. No Solana CLI. No Anchor CLI.
The CLI comes with `npx` — no global install needed.

### 2. Create a Program

```bash
npx @better-sol/cli create counter
# → Created programs/counter.ts
# → Generated keypair: CoUnTeR11111111111111111111111111111111111
# → Saved .better-sol/counter.json (private, gitignored)
```

This creates `programs/counter.ts` with working boilerplate — a counter account,
an initialize instruction, an increment instruction, and typed errors.
Like `laravel make:migration` — a starting point, not a framework.

You can also skip `create` and write the file from scratch. It's optional.

Edit the file to add your own logic:

```typescript
// programs/counter.ts
import { program, account, ix, defineErrors, u64, bool, pubkey, p } from 'better-sol/program'

const Counter = account({ count: u64, authority: pubkey, isActive: bool })
  .seeds('counter', '{authority}')

const errors = defineErrors({
  Unauthorized: 'Not the authority',
  NotActive: 'Counter is not active',
})

export const counter = program({
  name: 'counter', address: 'CouNTeR11111111111111111111111111111111111', errors, instructions: {
  initialize: ix({
    accounts: { counter: p.init(Counter), authority: p.signer() },
    args: { initialValue: u64 },
    run: ({ counter, authority }, { initialValue }) => {
      counter.count = initialValue
      counter.authority = authority
      counter.isActive = true
    },
  }),

  increment: ix({
    accounts: { counter: p.mut(Counter), authority: p.signer() },
    args: { amount: u64 },
    run: ({ counter, authority }, { amount }, ctx) => {
      ctx.require(authority === counter.authority, 'Unauthorized')
      ctx.require(counter.isActive, 'NotActive')
      counter.count += amount
    },
  }),
  },
})
```

The address was generated by `create`. You just write the logic.

One command. No keypair generation step. No config file.
`deploy` generates the keypair on first run and stores it in `.better-sol/`.

### 4. Use as Client — Same File

```typescript
// app.ts
import { betterSol } from 'better-sol'
import { counter } from './programs/counter'

const sol = betterSol({ cluster: 'devnet', programs: { counter } })

// Address comes from the program definition — it's in programs/counter.ts
const addr = counter.accounts.Counter.derive({ authority: sol.payer })

await sol.counter.initialize({ counter: addr, authority: sol.payer, initialValue: 42n })
const data = await counter.accounts.Counter.fetch(addr)
console.log(data.count) // → 42n
```

No address copy-pasted. No IDL. No code generation. No registration.
The program definition IS the client.

```diff
  const Counter = account({

+   isActive: bool,
+   lastUpdated: u64,  // ← add a field

```


`deploy` detects schema changes and warns about migrations. Programs are upgraded
in-place — same address, new code. Account data is preserved.

### 6. Test

```typescript
// counter.test.ts
import { createTestSol } from 'better-sol/testing'
import { counter } from './programs/counter'

const sol = createTestSol({ programs: { counter } })

const addr = counter.accounts.Counter.derive({ authority: sol.payer })

await sol.counter.initialize({ counter: addr, authority: sol.payer, initialValue: 0n })

await sol.counter.increment({ counter: addr, authority: sol.payer, amount: 5n })
await sol.counter.increment({ counter: addr, authority: sol.payer, amount: 3n })

const data = await counter.accounts.Counter.fetch(addr)
expect(data.count).toBe(8n)
```

No local validator. No `solana-test-validator`. `createTestSol` uses LiteSVM
under the hood — tests run in milliseconds, not seconds.

### 8. Use Someone Else's Program

```typescript
import { betterSol, fromIdl } from 'better-sol'
import { mangoIdl } from '@mango/idl'
import { counter } from './programs/counter'

const mango = fromIdl(mangoIdl)

const sol = betterSol({
  cluster: 'mainnet-beta',
  payer: './keypair.json',
  programs: {
    counter,  // ← your program (defined with better-sol)
    mango,    // ← someone else's program (from IDL)
  },
})

// All three work — methods appear on sol.programName
await sol.counter.increment({ ... })
await sol.mango.createAccount({ ... })
await sol.token.transfer({ ... })  // ← built-in, no registration needed
```

## The Invisible Infrastructure

The key principle: **infrastructure that the developer never thinks about.**

### Keypairs

The developer never runs `solana-keygen`. The `create` command handles everything.

- `create` generates a keypair, writes the address into the program file, saves the keypair to `.better-sol/`
- `deploy` generates a keypair if one doesn't exist yet
- The address is right in the source code — no resolution, no hidden files

The address lives in `programs/counter.ts` — it's a public key, safe in git.
The private key lives in `.better-sol/` — gitignored, only used by `deploy`.

This separation means:
- Anyone who clones the repo can **use** the program (address is in source code)
- Only people with the keypair can **deploy** upgrades (private key stays local or in secrets)
- CI/CD provides the keypair from a secret manager at deploy time

**Same keypair across all clusters.** The program has the same address on devnet,
testnet, and mainnet. PDA addresses are identical on every cluster. Client code
doesn't change between devnet and mainnet.

For mainnet security, after your program is deployed and tested,
set the upgrade authority to a multisig or governance account. After that,
the private key in `.better-sol/` can no longer upgrade the program — even if
leaked, it's useless.

### Program IDs and `declare_id!()`

The generated Rust includes `declare_id!()` from the keypair. The developer never
sees this — it's an implementation detail of the transpiler.

### IDL Publishing

Every `deploy` automatically publishes the Anchor IDL to:
- On-chain: via the program's metadata account (standard Anchor pattern)
- Cloud: `https://better-sol.fun/idl/{programId}/latest`

This means anyone can use `fromIdl()` to interact with programs built with better-sol.
Full ecosystem compatibility, zero effort.

### The .better-sol/ Directory

`.better-sol/` is infrastructure the developer never touches.
It's created automatically by `create` or `deploy`. **Gitignored.**

```
.better-sol/
  counter.json          ← program keypair (gitignored)
  amm.json              ← one keypair per program
```

One keypair per program, shared across all clusters.

```gitignore
# .gitignore
node_modules/
dist/
.better-sol/
```

For CI/CD, provide the keypair from a secret manager:
```bash
COUNTER_KEYPAIR=<base64> npx @better-sol/cli deploy --cluster mainnet-beta
```

For maximum security on mainnet, set upgrade authority to multisig after deployment.
Wallet keypairs must NEVER go in git — the `payer` keypair is separate and should
be stored in environment variables.

## Key Architecture Decisions

| Decision | Choice | Why |
|---|---|---|
| **Scope** | Library, not framework | Import a function, call it. No folder structure, no config files. |
| **Packages** | Runtime: `better-sol` (library) · CLI: `@better-sol/cli` (transpiler + deploy) | Library has no compiler code. CLI has no runtime code. |
| **Compilation** | Cloud (TS AST → Anchor Rust → cargo build-sbf → .so) | Developer never installs Rust. Like `drizzle-kit push`. |
| **Type safety** | `ctx` parameter (ElysiaJS pattern) | `ctx.require()`, `ctx.emit()`, `ctx.log()` — all compile-time checked |
| **Events** | `defineEvents()` + `ctx.emit()` | Event names autocomplete, data shapes validated field-by-field |
| **Validation** | Parse-time AST walking (not branded types) | Enforce supported operations with helpful error messages |
| **Escape hatch** | `` rust`...` `` tagged template | Raw Rust for edge cases the transpiler can't handle |
| **Same definition** | Program definition = client SDK | Zero code generation for our users. IDL auto-published for ecosystem compatibility |
| **Program address** | Named `address` parameter of `program()`, generated by `create` | Same address on all clusters. Public key in source, private key gitignored. |
| **Verification** | `deploy --verify` writes Rust, then `verify` submits to OtterSec | Two commands, no auto-commit. Generated Rust in user's own repo. |
| **Config** | Optional `better-sol.config.ts` (Paykit pattern) | No config file required. CLI auto-discovers `programs/**/*.ts`. |

## Error Messages That Help

### Before (raw @solana/kit)

```
Error: Transaction simulation failed: Error processing Instruction 0: custom program error: 0x1
```

What does `0x1` mean? Which account? Which instruction?

### After (better-sol)

```
❌ Unauthorized
   at programs/counter.ts, instruction "increment", line 8
   ctx.require(authority === counter.authority, 'Unauthorized')

   Instruction: increment
   Accounts: counter (CoUn...3xY), authority (Alic...7k2)
   Expected: authority === counter.authority
   Got: Alic...7k2 !== CoUn...3xY
```

Named errors with messages, source locations, and the actual values that failed.
This is what "developer experience" means.

## What's Not Here (Intentionally)

**No config file.** You don't write `better-sol.config.ts` unless you want to.
The defaults are: `programs/**/*.ts` for program discovery, `.better-sol/` for keypairs,
`devnet` for cluster. Everything auto-discovers.

**No build step.** The program definition works at runtime without compilation.
You import it, you use it. `deploy` is only for on-chain deployment, which is optional.

**No registration.** No `registerProgram()`. No `sol.addProgram()`. Programs are plugins
that you pass to `betterSol({ programs })`. They appear as methods automatically.

**No generated code.** No codegen step. No `generated/` folder (except for `--verify`).
The TypeScript you write IS the client. No intermediate representation needed.

**No framework.** No required folder structure. No required file names. No required
config format. Import a function, call it, get a thing back. Like Better Auth.

## Verified Results

- **AMM program**: 320 lines TS → generates 633 lines Anchor Rust, 7 instructions, 10 CPI calls
- **Token-2022 AMM**: 401 lines TS with `transferChecked`, works with Token-2022 extensions
- **Orderbook**: 357 lines TS → generates 478 lines zero-copy Rust with remaining accounts
- **Type safety**: All verified with `tsc --strict` — errors, events, token fields, remaining accounts, zero-copy arrays
- **Transpiler coverage**: 93% of operations (85/91), 76% of program types at 100%
- **Escape hatch**: ~5% of real-world programs need inline Rust (Metaplex, CLAMM tick math)
