## 1. Official SDK Architecture — Layered Design

Solana's official SDK is organized into five layers with clear separation of concerns:

### Layer 1: Core Types (Rust)
Crates in `anza-xyz/solana-sdk` — each is a tiny, focused crate:
- `solana-pubkey` — Address types, PDA derivation, ID macros
- `solana-instruction` — `Instruction`, `AccountMeta`, `InstructionError`
- `solana-account-info` — `AccountInfo` (onchain account view)
- `solana-account` — Offchain `Account` type
- `solana-signer` — `Signer` trait + `Keypair` implementation
- `solana-signature` — 64-byte `Signature` type
- `solana-transaction` — `Transaction`, `SanitizedTransaction`
- `solana-message` — `Message`, `TransactionMessage` types
- `solana-program-error` — `ProgramError`, `ProgramResult`
- `solana-clock`, `solana-rent`, `solana-epoch-schedule` — Sysvar types
- `solana-cpi` — `invoke`, `invoke_signed` helpers
- `solana-program-memory` — Low-level memory ops
- `solana-program-pack` — `Pack` trait for account serialization
- `solana-sysvar` — Sysvar accessor trait
- `solana-serde`, `solana-short-vec` — Compact serialization helpers
- `solana-borsh` — Borsh v1 compatibility

Pattern: **One crate per concept**. Every crate is potentially usable independently.

### Layer 2: Program SDK (Rust, onchain)
- **`solana-program`** — Aggregation crate for onchain programs
  - Re-exports core types
  - Provides `entrypoint!` macro
  - Provides program ID macros (`declare_id!`, `pubkey!`)
  - Provides sysvar accessors
  - Provides CPI helpers
  - Designed for `no_std` + `target_os = "solana"` compilation
  - Does NOT provide: IDL, account validation, instruction dispatch (these are Anchor's job)

- **`pinocchio`** — Alternative onchain framework (zero external deps)
  - Even more minimal than `solana-program`
  - `program_entrypoint!` macro (no copies, no allocations)
  - `lazy_program_entrypoint` (more control over input parsing)
  - Sub-crates: `pinocchio-system`, `pinocchio-token`, `pinocchio-token-2022`, `pinocchio-associated-token-account`, `pinocchio-memo`
  - Status: Still in development (official docs warn it may change significantly)

### Layer 3: Interface Crates (Rust — bridge layer)
Shared type definitions and instruction constructors between onchain and offchain:
- `solana-system-interface` — System Program types + instruction builders
- `spl-token-interface` — Token Program types
- `spl-token-2022-interface` — Token-2022 types
- `spl-associated-token-account-interface` — ATA types
- `solana-compute-budget-interface` — Compute budget types
- `spl-memo-interface`, `spl-token-metadata-interface`, `spl-token-group-interface`

**Purpose**: Single source of truth for program interfaces. Both onchain programs (via CPI) and offchain clients use the same instruction types and PDAs.

### Layer 4: TypeScript Client Toolkit
- **`@solana/kit`** — The official TypeScript SDK
  - Replaces `@solana/web3.js` for new development
  - RPC client, subscriptions, transactions, signers, codecs
  - Instruction plans (parallel, sequential, messagePacker)
  - Transaction planners and executors
  - Reactive stores (for React/Svelte/Solid)
  - Compute unit estimation
  - Airdrop helpers
  - `sendAndConfirmTransactionFactory` — blockhash transactions
  - `sendAndConfirmDurableNonceTransactionFactory` — nonce transactions
  - `sendTransactionWithoutConfirmingFactory` — fire-and-forget

### Layer 5: TypeScript Program SDKs
Official autogenerated clients following a consistent pattern:
- **`@solana-program/token`** — Canonical example
- **`@solana-program/system`** — System program client
- **`@solana-program/token-2022`** — Token-2022 client
- **`@solana-program/associated-token-account`** — ATA client
- **`@solana-program/memo`**, **`@solana-program/token-metadata`**, **`@solana-program/token-group`**

Generated via **Codama** (autogeneration tool) from program specifications.

## 2. Official TypeScript Instruction Pattern

Every instruction in the official TypeScript SDKs follows this pattern:

### 2.1 Instruction Builder (pure function)
```typescript
// Signature: returns Instruction with typed accounts and data
function getMintToInstruction(input: MintToInput): MintToInstruction;

// Return type is:
Instruction<TProgram> &
  InstructionWithData<ReadonlyUint8Array> &
  InstructionWithAccounts<[...typed account metas]>;
```

Key properties:
- **Pure function** — no side effects, no RPC calls, no signers needed
- **Returns Instruction** — not a transaction, not a promise
- **Typed accounts** — uses branded types for account addresses
- **Typed data** — codec-based encoder/decoder for data

### 2.2 Data Codec (encode/decode)
```typescript
function getMintToInstructionDataEncoder(): FixedSizeEncoder<MintToInstructionDataArgs>;
function getMintToInstructionDataDecoder(): FixedSizeDecoder<MintToInstructionData>;
function getMintToInstructionDataCodec(): FixedSizeCodec<...>;

// Uses struct encoder pattern:
getStructEncoder([
  ['discriminator', getU8Encoder()],
  ['amount', getU64Encoder()],
]);
```

### 2.3 Instruction Parser (deserialize)
```typescript
function parseMintToInstruction<TProgram, TAccountMetas>(
  instruction: Instruction & InstructionWithAccounts & InstructionWithData
): ParsedMintToInstruction;
```

### 2.4 Account Meta Factory
```typescript
const getAccountMeta = getAccountMetaFactory(programAddress, 'programId');
// Produces typed AccountMeta with correct roles (writable, signer, etc.)
```

### 2.5 Automatic Account Role Detection
The official pattern uses TypeScript's conditional types to automatically determine account roles from input types:
```typescript
// If mintAuthority is a TransactionSigner → ReadonlySignerAccount
// If mintAuthority is a plain Address → plain ReadonlyAccount
TAccountMintAuthority extends TransactionSigner
  ? ReadonlySignerAccount & AccountSignerMeta
  : TAccountMintAuthority
```

## 3. Official Instruction Plan System

This is a critical architectural concept that `better-sol` currently lacks:

### 3.1 InstructionPlan Types
```typescript
type InstructionPlan =
  | SingleInstructionPlan     // One instruction
  | SequentialInstructionPlan // Must execute in sequence (divisible or not)
  | ParallelInstructionPlan   // Can execute in parallel
  | MessagePackerInstructionPlan; // Dynamic message packing
```

### 3.2 Composable Multi-Step Operations
Higher-level functions compose multiple instructions into plans:
```typescript
// createMint = system/createAccount + token/initializeMint2
function getCreateMintInstructionPlan(input, config): InstructionPlan {
  return sequentialInstructionPlan([
    getCreateAccountInstruction(...),    // CPI: system program
    getInitializeMint2Instruction(...),  // CPI: token program
  ]);
}

// mintToATA = createAssociatedTokenIdempotent + mintToChecked
function getMintToATAInstructionPlan(input, config): InstructionPlan {
  return sequentialInstructionPlan([
    getCreateAssociatedTokenIdempotentInstruction(...),
    getMintToCheckedInstruction(...),
  ]);
}
```

### 3.3 Transaction Planning Pipeline
```
InstructionPlan
  → TransactionPlanner (blockhash, feePayer, compute units, message splitting)
    → TransactionPlan
      → TransactionPlanExecutor (sign, send, confirm)
        → TransactionPlanResult
```

### 3.4 Message Packing for Large Instructions
For instructions that exceed transaction size limits:
```typescript
function getLinearMessagePackerInstructionPlan({
  totalLength: dataToWrite.length,
  getInstruction: (offset, length) => getWriteInstruction({ offset, data: ... }),
});
// Automatically splits across multiple transactions
```

### 3.5 Reallocation Pattern
For account resize:
```typescript
function getReallocMessagePackerInstructionPlan({
  totalSize: additionalDataSize,
  getInstruction: (size) => getExtendInstruction({ length: size }),
});
// Splits reallocation into REALLOC_LIMIT (10240) byte chunks
```

## 4. Official Transaction Execution Flow

### 4.1 Manual Pattern (maximum control)
```typescript
// 1. Build instruction
const instruction = getMintToInstruction({
  mint: mintAddress,
  token: tokenAddress,
  mintAuthority: authoritySigner,
  amount: 1000n,
});

// 2. Create transaction message
const { value: blockhash } = await rpc.getLatestBlockhash().send();
const txMessage = pipe(
  createTransactionMessage({ version: 0 }),
  tx => setTransactionMessageFeePayerSigner(feePayer, tx),
  tx => setTransactionMessageLifetimeUsingBlockhash(blockhash, tx),
  tx => appendTransactionMessageInstructions([instruction], tx),
);

// 3. Sign
const signedTx = await signTransactionMessageWithSigners(txMessage);

// 4. Send and confirm
await sendAndConfirmTransaction(signedTx, { commitment: 'confirmed' });
```

### 4.2 Plan Pattern (automatic planning)
```typescript
// 1. Build instruction plan
const plan = getCreateMintInstructionPlan({
  payer, newMint: mint, decimals: 2, mintAuthority: payer.address,
});

// 2. Convert to transaction plan (handles blockhash, CU estimation, splitting)
const transactionPlanner = createTransactionPlanner({
  createTransactionMessage: async () => { /* blockhash + feePayer */ }
});
const transactionPlan = await transactionPlanner(plan);

// 3. Execute (sign + send + confirm)
await client.sendTransactionPlan(transactionPlan);
```

### 4.3 Plugin Pattern (convenience, similar to better-sol)
```typescript
// With token program plugin:
await client.token.instructions
  .createMint({ newMint: mint, decimals: 2, mintAuthority: payer.address })
  .sendTransaction();
```

## 5. Comparison: better-sol vs Official SDK

### 5.1 Architecture Comparison

| Aspect | Official SDK | better-sol |
|--------|-------------|------------|
| **Program definition language** | Rust (solana-program / pinocchio / anchor) | TypeScript (transpiles to Anchor Rust) |
| **Instruction building** | Pure functions returning `Instruction` | Methods on program client returning `InstructionMethod` |
| **Transaction building** | Explicit: createMessage → appendInstructions → sign → send | Implicit in `.send()` |
| **Instruction plans** | First-class: parallel/sequential/messagePacker | `sol.steps()` — sequential only |
| **Account typing** | Branded types + conditional role inference | Custom mapped types with AutoAccountConstraintKind |
| **Data serialization** | Struct encoder/decoder pattern (codecs) | Borsh encoder/decoder |
| **Program deployment** | `solana program deploy` (CLI) | `better-sol deploy` (wraps compiler API) |
| **Client generation** | Codama autogeneration from IDL spec | `fromIdl()` + program definition types |
| **Rent exemption** | RPC `getMinimumBalanceForRentExemption` | Same (but no local computation fallback — good!) |
| **Key management** | `solana-keychain` (multi-backend) | Basic wallet adapters + secretKey/keypairFile |

## 6. Design Evaluation

### 6.1 Transpiler Approach — CORRECT but incomplete

**Assessment**: The core idea (write TypeScript → get Anchor Rust + typed client) is sound and has no equivalent in the official ecosystem. However:

**Correct aspects**:
- ✅ Target output: Anchor Rust (widely used, IDL-compatible)
- ✅ Generated Rust is clean, warning-free, properly scoped
- ✅ Strong type safety throughout the pipeline
- ✅ 18 failure fixtures for unsupported patterns (correctly rejects what can't be translated)

**Missing aspects**:
- ❌ Generated client SDK doesn't follow official `@solana-program/*` patterns
- ❌ No pure instruction builder export (`getXxxInstruction()`)
- ❌ No instruction parser export (`parseXxxInstruction()`)
- ❌ No separate codec exports (users can't decode/encode manually)
- ❌ No instruction plan composability with official plans

### 6.2 Client SDK Architecture — MIXED

**Good**:
- ✅ Strong type safety with `@solana/kit` types
- ✅ Automatic account role detection
- ✅ `derived()` PDA with seed validation
- ✅ Zero-copy struct support
- ✅ Token-2022 first class
- ✅ Unsigned instruction building support

**Problematic**:
- ⚠️ Conflates instruction building + transaction creation + sending into one API
- ⚠️ No separation of instruction plans vs execution
- ⚠️ No message packer support for large instructions
- ⚠️ No transaction planner abstraction
- ⚠️ `steps()` is sequential-only (no parallel plans)
- ⚠️ Instruction methods return `InstructionMethod` (custom type) instead of `Instruction` + `InstructionPlan` from `@solana/kit`

### 6.3 Key Design Risks

**Risk 1: API divergence from official patterns**
As the official SDK evolves, `better-sol`'s wrapper API may become incompatible or confusing. Users who learn `better-sol` won't easily transition to the official pattern and vice versa.

**Mitigation**: The generated client should export both the convenience API AND the official-pattern API.

**Risk 2: Transaction lifecycle conflation**
Building instructions, signing, and sending are separate concerns. The official SDK intentionally separates them. `better-sol` combines them, making it harder to:
- Compose instructions from multiple programs
- Pre-build transactions for offchain signing
- Use wallet adapters in the middle of the flow
- Implement custom confirmation strategies

**Mitigation**: Offer `.instruction()` and `.plan()` methods alongside `.send()`.

**Risk 3: Missing compute unit estimation**
Without CU estimation, transactions may exceed budgets or waste CU. The official SDK provides `estimateComputeUnitLimitFactory`.

**Mitigation**: Add CU estimation support.

**Risk 4: getMinimumBalanceForRentExemption deprecation**
The `@solana/kit` README marks this as deprecated (will be removed in v7). SIMD-0437 is actively reducing rent costs. Our token client and createMint use rent calculations.

**Mitigation**: Use the RPC method instead of local computation. Track SIMD-0194 and SIMD-0389 for dynamic rent changes.

**C. Export codec functions**
```typescript
const encoder = sol.counter.initialize.codec();
```

### 7.2 Near-term (feature parity)

**D. Add compute unit estimation**
```typescript
const sol = await betterSol({ cluster: "devnet", payer, programs: { counter } });
```

**E. Add transaction planner integration**
```typescript
const planner = sol.createTransactionPlanner();
```

For programs with large account data or many instructions.

## 8. Transpiler Architecture — Full Assessment

### 8.1 Current pipeline
```
TypeScript program definition
  → ts-morph AST parsing
    → IR (intermediate representation)
      → Anchor Rust generator (lib.rs, Cargo.toml, IDL)
      → Client SDK type inference (from program definition types)
```

### 8.2 Is this correct?

**YES** — The transpiler approach is correct for the following reasons:

1. **Official ecosystem provides no TypeScript → Rust path**
   - Rust is the only supported onchain language
   - No official TS-to-Rust transpiler exists
   - Anchor is the most widely used Rust framework
   - Target output (Anchor Rust) is compatible with the official ecosystem

2. **IR-based transpiler is the right design**
   - Separate IR from codegen enables multiple output targets
   - TypeScript AST → IR → Rust is a proven pattern
   - IR enables future output targets (Pinocchio, raw solana-program, etc.)

3. **Failure fixtures ensure safety**
   - 18 fixtures test unsupported patterns
   - Rejects patterns that can't be reliably translated
   - This is the correct approach: be conservative about what you accept

### 8.3 Potential transpiler improvements

1. **Output target: Pinocchio**
   - For users who want zero-dependency programs
   - Would produce even smaller `.so` files
   - Lower priority than Anchor output (Anchor is more widely used)

2. **Output target: Interface crate**
   - Generate `spl-<name>-interface` Rust crate alongside the program
   - This would follow the official pattern of interface crates
   - Would enable interop with official Rust client libraries

3. **Source maps**
   - Map generated Rust code back to original TypeScript source
   - Useful for debugging and verification

## 9. Official Patterns We Should Follow

### 9.1 Follow These
| Pattern | Why |
|---------|-----|
| Pure instruction builders | Composability, separation of concerns |
| `InstructionPlan` composability | Interop with official SDK |

## 10. Summary

### What better-sol gets RIGHT:
1. **TypeScript-first program definition** — genuine innovation, no official equivalent
2. **Anchor Rust output** — correct target, widely compatible
3. **Strong type safety** — competitive with official SDK
4. **Automatic account role detection** — following official pattern
5. **Token-2022 first class** — ahead of official Token SDK
6. **Zero-copy support** — not available in official TypeScript SDKs
7. **Wallet adapter integration** — convenient, official SDK doesn't provide this

### What better-sol is MISSING:
1. **Pure instruction builders** — should export `getXxxInstruction()` alongside convenience API
2. **Instruction plan composability** — should return `InstructionPlan` objects
3. **Transaction planner abstraction** — separate message building from signing from sending
4. **Compute unit estimation** — important for production transactions
5. **Instruction parsers** — useful for explorers and indexers
6. **Message packer support** — for large instructions/accounts

### Design conflicts (need attention):
1. **Instruction lifecycle conflation** — `.send()` does too much; should offer `.instruction()` too
2. **Custom return types** — `InstructionMethod` instead of official `Instruction`
3. **`steps()` limited to sequential** — no parallel or messagePacker plans

### No fundamental design mistakes found:
- The core transpiler approach is correct
- The TypeScript-first value proposition is unique
- The Anchor target is the right choice
- The IR-based architecture is sound
- The unsupported-pattern approach is conservative and safe
