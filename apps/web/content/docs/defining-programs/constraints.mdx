---
title: Constraints
description: Account constraints tell Better Sol how each account is used in an instruction.
---

When you write an instruction, every account in the `accounts` object is paired with a constraint. The constraint does two things: it tells Better Sol what role the account plays (create it, read it, close it), and it determines what the `run()` body receives. A `bs.init(Counter)` gives you `counter.count` and other fields to write to. A `bs.signer()` gives you a string address. A `bs.clock()` gives you the current timestamp.

## User-defined account constraints

These constraints reference one of your account definitions. They make the account writable and give you typed access to the account data.

### `bs.init(account)`: Create a new account

```ts
initialize: ix({
  accounts: {
    counter: bs.init(Counter),
    authority: bs.signer(),
  },
  args: { initialValue: bs.u64() },
  run: ({ counter, authority }, { initialValue }) => {
    counter.count = initialValue
    counter.authority = authority
    counter.isActive = true
  },
}),
```

`bs.init()` creates a brand-new account. If the account has `.derive()` seeds, it creates a PDA at that address. If not, it creates the account with a freshly-generated keypair.

All fields start at their default values: `0n` for big integers, `0` for small integers, `false` for booleans, `""` for strings, `null` for optionals, and all-zero bytes for pubkeys. You set the real values in the `run()` body.

The system program is included automatically whenever `bs.init()` appears. You never need to add it yourself.

### `bs.initIfNeeded(account)`: Create only if it does not exist

```ts
createOrIncrement: ix({
  accounts: {
    counter: bs.initIfNeeded(Counter),
    authority: bs.signer(),
  },
  args: { initialValue: bs.u64() },
  run: ({ counter, authority }, { initialValue }) => {
    if (counter.count === 0n) {
      counter.count = initialValue
      counter.authority = authority
    }
    counter.count += 1n
  },
}),
```

Use this for "create or update" patterns. If the account does not exist yet, it is created with default values. If it already exists, its data is preserved and you can modify it. This is useful when you want a single instruction that works whether the account exists or not.

### `bs.mut(account)`: Read and write an existing account

```ts
increment: ix({
  accounts: {
    counter: bs.mut(Counter),
    authority: bs.signer(),
  },
  args: { amount: bs.u64() },
  run: ({ counter, authority }, { amount }, ctx) => {
    ctx.require(authority === counter.authority, "Unauthorized")
    counter.count += amount
  },
}),
```

This is the most common constraint. You can both read and write the account's fields. The account must already exist. If it does not, the transaction fails.

### `bs.close(account, refundTo)`: Close an account and reclaim rent

```ts
close: ix({
  accounts: {
    counter: bs.close(Counter, "authority"),
    authority: bs.signer(),
  },
  run: () => {
    // Account is closed, rent reclaimed by authority
  },
}),
```

The second argument (`"authority"`) is the name of another account in the same instruction that receives the reclaimed rent lamports. After this instruction, the account no longer exists. Its data is zeroed out and its lamports are transferred to the refund target.

### `bs.realloc(account, space)`: Resize an account

```ts
resize: ix({
  accounts: {
    data: bs.realloc(Data, 512),
    authority: bs.signer(),
  },
  run: ({ authority }, ctx) => {
    ctx.require(authority === data.authority, "Unauthorized")
  },
}),
```

`bs.realloc()` changes the data size of an existing account to the number of bytes given as the second argument. This is useful when an account holds variable-length data (like a string or vector) and needs more space. The system program is included automatically.

You can also use `bs.realloc()` to shrink an account by passing a smaller size value.

## System constraints

These constraints provide access to well-known Solana programs and system variables. They do not reference an account definition.

### `bs.signer()`: The transaction signer

```ts
increment: ix({
  accounts: {
    counter: bs.mut(Counter),
    authority: bs.signer(),
  },
  run: ({ counter, authority }, { amount }, ctx) => {
    ctx.require(authority === counter.authority, "Unauthorized")
  },
}),
```

`bs.signer()` represents the wallet or keypair that signed the transaction. On the client, `authority` is a `string` (base58 address). It is read-only: you cannot modify the signer's data through this constraint.

On the client side, you can omit the signer when calling the instruction. Better Sol automatically fills it in with the payer's address:

```ts
await sol.counter.increment({
  counter: counterAddr,
  amount: 5n,
  // authority is optional, filled with sol.payer
})
```

### `bs.mint()`: A Token mint account

```ts
mintTo: ix({
  accounts: {
    mint: bs.mint(),
    to: bs.tokenAccount().writable(),
    authority: bs.signer(),
  },
  run: ({ mint, to, authority }) => {
    // mint.key is the mint's address
    // mint.supply is total supply (bigint)
    // mint.decimals is decimal places (number)
    // mint.mintAuthority is the mint authority address or null
    // mint.freezeAuthority is the freeze authority address or null
  },
}),
```

`bs.mint()` is read-only by default. If you need to modify the mint (for example, changing its authority), use `.writable()`:

```ts
mint: bs.mint().writable(),
```

### `bs.tokenAccount()`: A Token account

```ts
transfer: ix({
  accounts: {
    from: bs.tokenAccount().writable(),
    to: bs.tokenAccount().writable(),
    authority: bs.signer(),
  },
  run: ({ from, to, authority }) => {
    // from.key is the token account address
    // from.mint is the mint this account belongs to
    // from.owner is the owner of this account
    // from.amount is the balance (bigint)
  },
}),
```

`bs.tokenAccount()` is read-only by default. Chain `.writable()` for transfers, burns, and other modifications:

```ts
from: bs.tokenAccount().writable(),
```

### `bs.tokenProgram()` and `bs.token2022Program()`

```ts
tokenProgram: bs.tokenProgram(),
token2022Program: bs.token2022Program(),
```

These give you a `TokenProgramInfo` object with a `key` field pointing to the respective program address. `bs.tokenProgram()` is automatically included when `bs.mint()` or `bs.tokenAccount()` appears in an instruction. You only need it explicitly for Token-2022 operations or advanced use cases.

### `bs.systemProgram()`: The System program

```ts
systemProgram: bs.systemProgram(),
```

Gives you the System program address. Automatically included whenever `bs.init()` is present. You rarely need to add it manually.

### `bs.clock()`: The Clock sysvar

```ts
expireListing: ix({
  accounts: {
    listing: bs.mut(Listing),
    authority: bs.signer(),
    clock: bs.clock(),
  },
  run: ({ listing, authority, clock }, ctx) => {
    ctx.require(authority === listing.authority, "Unauthorized")
    ctx.require(clock.unixTimestamp >= listing.expiresAt, "NotExpired")
    listing.isActive = false
  },
}),
```

`bs.clock()` gives you access to the on-chain clock. It provides three fields:

- `unixTimestamp` (`bigint`): current Unix timestamp in seconds
- `slot` (`bigint`): the current slot
- `epoch` (`bigint`): the current epoch

Use it for time-based conditions like expiration checks, timelocks, or any logic that depends on when the transaction executes.

Alternatively, you can get just the timestamp inside a `run()` body using `cpi.sol.timestamp()`, which returns the same value as `clock.unixTimestamp`:

```ts
run: ({ listing }, ctx) => {
  const now = cpi.sol.timestamp()
  ctx.require(now >= listing.expiresAt, "NotExpired")
}
```

## Remaining accounts

```ts
batchProcess: ix({
  accounts: {
    authority: bs.signer(),
    items: bs.remaining(Item),
  },
  run: ({ items, authority }) => {
    for (let i = 0; i < items.length; i++) {
      items[i].value += 1n
    }
  },
}),
```

`bs.remaining()` provides a dynamic list of accounts that the caller passes at transaction time. Each element has the fields from the account definition plus a `key` field for the address.

On the client, you pass an array of addresses:

```ts
await sol.escrow.batchProcess({
  authority: sol.payer,
  remainingAccounts: [item1Addr, item2Addr, item3Addr],
})
```

This is useful for batch operations where the number of accounts varies per call.
