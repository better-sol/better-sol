All type tokens in Better Sol live under the `bs` namespace. You never import individual types. Instead you call `bs.u64()`, `bs.optional()`, `bs.vector()`, and so on. Each call returns a typed token that Better Sol uses to serialize your data on-chain and infer TypeScript types on the client.

```ts
import { bs } from "better-sol/program"
```

## Integers

Solana accounts store integers as raw bytes. The type you choose determines how many bytes are used and whether the value can be negative. The TypeScript mapping follows a simple rule: types up to 32 bits map to `number`, and anything 64 bits or wider maps to `bigint`.

```ts
const Counter = bs.account({
  count: bs.u64(),       // bigint (balances, amounts, timestamps)
  bump: bs.u8(),         // number (small values like bump seeds and flags)
  id: bs.u32(),          // number (identifiers, indices)
  balance: bs.i64(),     // bigint (signed values like offsets or deltas)
})
```

| Type | TypeScript | Width | Use when |
|---|---|---|---|
| `bs.u8()` | `number` | 8-bit unsigned | Bump seeds, small flags, enum variants |
| `bs.u16()` | `number` | 16-bit unsigned | Token decimals, string/vector lengths |
| `bs.u32()` | `number` | 32-bit unsigned | Account sizes, instruction indices |
| `bs.u64()` | `bigint` | 64-bit unsigned | Balances, token amounts, timestamps, counters |
| `bs.u128()` | `bigint` | 128-bit unsigned | Very large numbers, mathematical fields |
| `bs.i8()` | `number` | 8-bit signed | Small negative values |
| `bs.i16()` | `number` | 16-bit signed | Temperature, offsets |
| `bs.i32()` | `number` | 32-bit signed | General-purpose signed integers |
| `bs.i64()` | `bigint` | 64-bit signed | Signed timestamps, deltas |
| `bs.i128()` | `bigint` | 128-bit signed | Large signed values |

The practical rule is straightforward: use `u64` for anything that holds an amount or a count, `u8` for bump seeds and small flags, `pubkey` for addresses, and `i64` when you need negative numbers.

## Booleans and addresses

```ts
const Profile = bs.account({
  isAdmin: bs.bool(),       // boolean
  authority: bs.pubkey(),   // string (a base58 Solana address)
  name: bs.string(),        // string (UTF-8, length-prefixed)
  metadata: bs.bytes(),     // Uint8Array (raw binary data)
})
```

**`bool()`** stores as a single byte (`0` or `1`). It cannot appear inside zero-copy accounts. Use `u8()` with an explicit `=== 1` check instead if you need a boolean in a zero-copy context.

**`pubkey()`** stores as 32 bytes. It is the type you use for every address reference: authorities, mints, owners, and PDA seeds that reference other accounts. On the TypeScript side it is a base58 `string`.

**`string()`** is length-prefixed UTF-8. Avoid it in hot paths or large data sets because variable-length strings are expensive on-chain. Prefer fixed-size alternatives when possible.

**`bytes()`** is length-prefixed raw binary. Use it for arbitrary binary data like hashes, signatures, or serialized blobs.

## Optional values

`bs.optional()` wraps another type to allow `null`:

```ts
const Profile = bs.account({
  nickname: bs.optional(bs.string()),   // string | null
  delegate: bs.optional(bs.pubkey()),   // string | null
  maxStake: bs.optional(bs.u64()),      // bigint | null
})
```

When the value is present, it is preceded by a single byte: `1` for present, `0` for null. Use optional for fields that are not always filled in, like a nickname that a user might not set, or a delegate that can be revoked.

On the TypeScript side, you pass `null` to set the field to null, or the actual value otherwise:

```ts
await sol.profile.initialize({
  profile: addr,
  nickname: null,       // not set
  delegate: someAddr,    // set
  maxStake: null,       // not set
})
```

## Dynamic-length arrays

`bs.vector()` creates an array with a maximum number of entries. The length is stored as a 4-byte prefix followed by the elements:

```ts
const Leaderboard = bs.account({
  topScores: bs.vector(bs.u64()),            // up to 32 entries of bigint
  recentPlayers: bs.vector(bs.pubkey(), 10),  // up to 10 entries of string
})
```

The default maximum is 32 entries. Pass a different number as the second argument if you need more or fewer. The maximum is enforced during serialization: if you pass a longer array, it throws. This maximum exists because on-chain accounts have a fixed size, and the system needs to know the worst-case space requirement.

On the TypeScript side, the vector maps to a regular array type:

```ts
// topScores is bigint[]
// recentPlayers is string[]
await sol.leaderboard.update({
  leaderboard: addr,
  topScores: [100n, 200n, 300n],
  recentPlayers: [addr1, addr2, addr3],
})
```

## Fixed-length arrays

`bs.array()` creates an array with an exact, fixed number of entries. No length prefix is needed because the size is always the same:

```ts
const Multisig = bs.account({
  signers: bs.array(bs.pubkey(), 3),   // exactly 3 signer addresses
  votes: bs.array(bs.bool(), 5),        // exactly 5 vote flags
})
```

The difference from `vector` matters on-chain. Fixed arrays occupy a predictable amount of space: 3 pubkeys is always 96 bytes, no prefix needed. Vectors need that 4-byte length prefix plus up to `maxEntries * elementSize` bytes of space reserved.

On the TypeScript side, these arrays have a `length` property set to the declared size, which helps TypeScript understand the exact shape:

```ts
// signers: { length: 3; [index: number]: string }
// votes: { length: 5; [index: number]: boolean }
```

Use `array` when you always have the same number of elements (like signers in a multisig). Use `vector` when the number varies (like a list of scores that grows over time).

## Zero-copy restrictions

Zero-copy accounts trade flexibility for read speed. They can only contain types that have a fixed, known byte layout. The allowed types are:

- All integer types (`u8` through `i128`)
- `f32` and `f64`
- `pubkey`
- Structs created with `bs.struct()` (see [Accounts](/docs/defining-programs/accounts))

These types are **not allowed** in zero-copy accounts because they have variable or dynamic layouts:

- `bool` (not a fixed Pod type; use `u8()` with an explicit check instead)
- `string` (variable length)
- `bytes` (variable length)
- `optional()` (needs a discriminator byte)
- `vector()` (variable length)

If you try to use a restricted type inside a zero-copy account, TypeScript will flag it immediately:

```ts
// TypeScript error: bool is not allowed in zero-copy accounts
const BadZC = bs.account({
  flag: bs.bool(),   // ← error here
}).zeroCopy()
```

## Type inference

You almost never write TypeScript types yourself. Better Sol infers everything from the program definition. The type tokens carry the information through, and the generic types on the SDK resolve the rest automatically.

When you do need to reference a type (for example, in a utility function), two helper types are available:

```ts
import { bs, InferType, InferFields } from "better-sol"

// InferType gives you the TypeScript type for a single field token:
type Count = InferType<typeof bs.u64>             // bigint
type Flag = InferType<typeof bs.bool>             // boolean
type MaybeName = InferType<ReturnType<typeof bs.optional<typeof bs.string>>>  // string | null

// InferFields gives you the full object shape from an account definition:
type CounterData = InferFields<typeof Counter.fields>
// { count: bigint; authority: string; isActive: boolean }
```

In practice you rarely need these. The client SDK infers argument types, account data shapes, and event payloads all from the program definition you pass to `betterSol()`.
