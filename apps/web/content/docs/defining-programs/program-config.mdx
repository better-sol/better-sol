title: Program Config

The program config is the top-level object that brings everything together. It holds your accounts, instructions, errors, and events in one place. This is what you pass to `betterSol()` on the client, and what the CLI deploys.

## The full program definition

```ts
import { bs, cpi } from "better-sol/program"

const Counter = bs.account({
  count: bs.u64(),
  authority: bs.pubkey(),
  isActive: bs.bool(),
}).derive(seed => ["counter", seed.authority])

export const counter = bs.program({
  name: "counter",
  address: "91eZUq6pokUtTcucXV1BVCAaarMy7EiHWv3SogYNZ7xs",
  accounts: { Counter },
  errors: {
    Unauthorized: "Only the authority can update this counter",
    NotActive: "Counter is not active",
  },
  events: {
    Incremented: { newCount: bs.u64(), authority: bs.pubkey() },
  },
}, ix => ({
  initialize: ix({
    accounts: {
      counter: bs.init(Counter),
      authority: bs.signer(),
    },
    args: { initialValue: bs.u64() },
    run: ({ counter, authority }, { initialValue }) => {
      counter.count = initialValue
      counter.authority = authority
      counter.isActive = true
    },
  }),

  increment: ix({
    accounts: {
      counter: bs.mut(Counter),
      authority: bs.signer(),
    },
    args: { amount: bs.u64() },
    run: ({ counter, authority }, { amount }, ctx) => {
      ctx.require(authority === counter.authority, "Unauthorized")
      ctx.require(counter.isActive, "NotActive")
      counter.count += amount
      ctx.emit("Incremented", { newCount: counter.count, authority })
    },
  }),

  close: ix({
    accounts: {
      counter: bs.close(Counter, "authority"),
      authority: bs.signer(),
    },
    run: () => {},
  }),
}))
```

## Config fields

| Field | Type | Required | Description |
|---|---|---|---|
| `name` | `string` | Yes | The program name. Used as the on-chain module name. Must be a valid identifier: lowercase letters, numbers, and underscores. This is also how you reference the program on the client (`sol.counter`). |
| `address` | `string` | Yes | The on-chain program ID (base58 address). The CLI generates this when you run `create`. |
| `accounts` | `Record<string, AccountDefinition>` | No | Account definitions registered for the client. Without this, `.derive()` and `.fetch()` are not available. |
| `errors` | `Record<string, string>` | No | Error definitions. Keys are error names used in `ctx.require()`, values are human-readable messages. |
| `events` | `Record<string, FieldSchema>` | No | Event definitions. Keys are event names used in `ctx.emit()`, values are field schemas defining the payload. |

## The `ix` callback

The second argument to `bs.program()` is a function that receives `ix` and returns an object of instruction definitions:

```ts
bs.program({ ... }, ix => ({
  initialize: ix({ ... }),
  increment: ix({ ... }),
  close: ix({ ... }),
}))
```

Each key becomes a method on the client. You call it as `sol.counter.initialize()`, `sol.counter.increment()`, and so on. The key is also used as the instruction identifier, converted to snake_case for the on-chain name. So `incrementCount` becomes `increment_count`.

## Where the program address comes from

The `address` field is the permanent on-chain identity of your program. It is generated when you run `create`:

```bash
npx @better-sol/cli@latest create counter
```

This outputs the address and stores the keypair at `.better-sol/counter.json`. The keypair is used for deployment. Never commit it to git; the `init` command already adds `.better-sol/` to your `.gitignore`.

## Registering accounts

The `accounts` field in the program config serves two purposes:

1. **Client-side derivation.** Only accounts listed here get `.derive()` and `.fetch()` methods on the client. If you forget to register an account, you will not be able to derive its PDA address or fetch its data.

2. **Constraint resolution.** When you reference an account definition like `bs.init(Counter)` or `bs.mut(Counter)` in an instruction, Better Sol looks it up by name. The name in the `accounts` object must match the variable name you pass to the constraint.

```ts
// Without accounts, these would not work:
// sol.counter.accounts.Counter.derive({ authority: addr })
// sol.counter.accounts.Counter.fetch(addr)
```

You only need to register accounts that the client interacts with directly. Internal accounts that are never fetched or derived can be omitted.

## Passing the program to the client

On the client side, you pass the program definition to `betterSol()`:

```ts
import { betterSol, keypairFile } from "better-sol"
import { counter } from "./programs/counter"

const sol = await betterSol({
  cluster: "devnet",
  payer: keypairFile("./keypair.json"),
  programs: { counter },
})
```

Every program in the `programs` object becomes a namespace on the client. The key (`counter`) must match the `name` field in the program config. Then you get:

- `sol.counter.increment()`: call instructions
- `sol.counter.accounts.Counter.derive()`: derive PDA addresses
- `sol.counter.accounts.Counter.fetch()`: fetch and decode account data
- `sol.counter.parseErrors()`: parse error logs
- `sol.counter.parseEvents()`: parse event logs

## Multiple programs

You can register as many programs as you need:

```ts
import { betterSol, keypairFile } from "better-sol"
import { counter } from "./programs/counter"
import { marketplace } from "./programs/marketplace"
import { governance } from "./programs/governance"

const sol = await betterSol({
  cluster: "devnet",
  payer: keypairFile("./keypair.json"),
  programs: { counter, marketplace, governance },
})

// All programs are available:
await sol.counter.increment({ counter: addr, amount: 5n })
await sol.marketplace.list({ item: itemAddr, price: 100n })
await sol.governance.vote({ proposal: proposalAddr, choice: 1 })
```

Each program is independent. They can share accounts, call each other via CPI, and be deployed separately.

## Type inference

The program definition is the single source of truth. TypeScript infers everything from it, so you never need to write client-side types by hand.

The instruction parameters, account data shapes, error names, and event payloads are all inferred:

```ts
// Instruction argument types are inferred from the instruction definition
// sol.counter.increment expects: { counter: string; amount: bigint }

// Account data types are inferred from the account definition
// sol.counter.accounts.Counter.fetch resolves to:
// { count: bigint; authority: string; isActive: boolean } | null

// Error names are validated against the errors object
ctx.require(condition, "Unauthorized")  // valid
ctx.require(condition, "FooError")       // TypeScript error: not in errors

// Event payload types match the field schema exactly
ctx.emit("Incremented", { newCount: counter.count, authority })
// TypeScript checks that newCount is bigint and authority is string
```

This means if you add a field to an account, rename an error, or change an event's payload, the type errors propagate to every file that uses the program. There is no separate step to keep things in sync.
