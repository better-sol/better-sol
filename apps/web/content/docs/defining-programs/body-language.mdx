The `run()` body is the on-chain logic of your instruction. It supports a specific subset of TypeScript. Anything outside that subset produces a clear error telling you what to use instead. This page is a complete reference. If it is not listed here as supported, it is not supported.

## Reading and writing account fields

You can read any field from any account in your `accounts` object, and you can write to accounts that are marked writable (those using `bs.init()`, `bs.mut()`, `bs.initIfNeeded()`, `bs.close()`, or `bs.realloc()`):

```ts
run: ({ counter, authority }, { amount }, ctx) => {
  // Read
  ctx.require(counter.isActive, "NotActive")

  // Write
  counter.count += amount
  counter.authority = authority
  counter.isActive = false
  counter.label = null   // clear an optional field
}
```

Assignment (`=`) and compound assignment (`+=`, `-=`, `*=`) are both supported for numeric fields. Setting an optional field to `null` clears it.

## Conditional logic

### if / else

```ts
run: ({ counter }, { amount }, ctx) => {
  if (counter.count >= amount) {
    counter.count -= amount
  } else {
    ctx.require(false, "BelowZero")
  }
}
```

Both `if` and `if/else` are supported. There is no `else if` construct. For multiple conditions, use nested `if/else` blocks.

### Ternary expressions

```ts
run: ({ counter }) => {
  counter.isActive = counter.count > 0n ? true : false
}
```

Ternary expressions work in assignments. The condition must be a boolean expression, and both branches must produce the same type.

## Loops

### Bounded for loops

```ts
run: ({ items }) => {
  for (let i = 0; i < items.length; i++) {
    items[i].value += 1n
  }
}
```

For loops must have an explicit, bounded end condition (`i < limit`). The following are not supported: `for...of`, `for...in`, and `while` loops.

## Arithmetic

All standard arithmetic operators are supported:

```ts
run: ({ counter }, { amount }) => {
  counter.count += amount       // addition
  counter.count -= 1n          // subtraction
  counter.count *= 2n          // multiplication
  const total = counter.count + amount  // arithmetic in expressions
}
```

Division and modulo are not supported because they add complexity on-chain. Use multiplication for ratios instead.

## Comparison and boolean logic

```ts
run: ({ counter, authority }, ctx) => {
  ctx.require(counter.count > 0n, "BelowZero")
  ctx.require(authority === counter.authority, "Unauthorized")
  ctx.require(counter.isActive && counter.count > 0n, "NoOperation")

  // Negation
  counter.isActive = !counter.isActive
}
```

Equality (`===`, `!==`), comparison (`>`, `<`, `>=`, `<=`), logical AND (`&&`), logical OR (`||`), and boolean negation (`!`) are all supported.

## Require

```ts
ctx.require(condition, "ErrorName")
```

This is the only way to throw an error in a `run()` body. If `condition` is `false`, the transaction fails with the named error. The error name must exist in your program's `errors` config. Better-sol validates this before deployment: if you mistype the error name, you get an error immediately.

```ts
ctx.require(authority === counter.authority, "Unauthorized")  // valid
ctx.require(condition, "FooError")  // error: not in errors map
```

Multiple `ctx.require()` calls in a row are fine. They are checked in order, and the first one that fails stops the transaction:

```ts
run: ({ counter, authority }, { amount }, ctx) => {
  ctx.require(authority === counter.authority, "Unauthorized")
  ctx.require(counter.isActive, "NotActive")
  ctx.require(counter.count >= amount, "BelowZero")
  counter.count -= amount
}
```

## Emit

```ts
ctx.emit("EventName", { field1: value1, field2: value2 })
```

Emits a structured event. The event name must exist in your program's `events` config. The payload must match the field schema exactly. Missing fields or extra fields cause an error.

```ts
ctx.emit("Incremented", { newCount: counter.count, authority })  // valid
ctx.emit("Incremented", { newCount: counter.count })  // error: missing "authority"
```

You can emit multiple events in a single instruction:

```ts
run: ({ listing }, ctx) => {
  ctx.emit("Deactivated", { reason: "expired" })
  ctx.emit("Refunded", { amount: listing.price })
}
```

## Log

```ts
ctx.log("Counter incremented by {}", amount)
ctx.log("Transfer from {} to {}", from, to)
```

Writes a formatted message to the transaction log. Curly braces `{}` are placeholders that get filled with the provided values. Only string, number, bigint, boolean, and address values can be interpolated.

## Return values

```ts
getCount: ix({
  accounts: {
    counter: bs.mut(Counter),
  },
  returns: bs.u64(),
  run: ({ counter }) => {
    return counter.count
  },
}),
```

Add a `returns` field to the instruction config with any type token. Then use `return` in the `run()` body. The returned value is available to the caller through simulation.

You can also return expressions:

```ts
return counter.count * 2n
return counter.isActive
```

## Cross-program invocations (CPI)

The `cpi` object provides typed cross-program invocations inside `run()` bodies:

```ts
import { cpi } from "better-sol/program"

mintTo: ix({
  accounts: {
    mint: bs.mint(),
    to: bs.tokenAccount().writable(),
    authority: bs.signer(),
    tokenProgram: bs.tokenProgram(),
  },
  args: { amount: bs.u64() },
  run: ({ mint, to, authority }, { amount }) => {
    cpi.token.mintTo({ mint, to, authority, amount })
  },
}),
```

Supported CPI calls:

| Call | Parameters |
|---|---|
| `cpi.token.transfer()` | `{ from, to, authority, amount }` |
| `cpi.token.transferChecked()` | `{ from, to, mint, authority, amount, decimals }` |
| `cpi.token.mintTo()` | `{ mint, to, authority, amount }` |
| `cpi.token.burn()` | `{ from, mint, authority, amount }` |
| `cpi.sol.timestamp()` | (none) |

`cpi.token.transfer()` and the other token calls take the same parameter shapes as you see in the `accounts` constraints. The accounts come from the instruction's accounts, and the amounts come from the args.

`cpi.sol.timestamp()` returns the current Unix timestamp as a `bigint`:

```ts
run: ({ listing }, ctx) => {
  const now = cpi.sol.timestamp()
  ctx.require(now >= listing.expiresAt, "NotExpired")
}
```

CPI calls are turned into on-chain cross-program invocations. At runtime in TypeScript, they do nothing (they are placeholders that Better Sol reads during deployment).

## Accessing constraint values in the body

Accounts declared with `bs.signer()`, `bs.mint()`, `bs.tokenAccount()`, `bs.clock()`, and `bs.systemProgram()` all provide typed values in the `run()` body:

```ts
run: ({ authority, mint, clock }) => {
  // authority (from bs.signer()) is a string — the signer's address
  // mint (from bs.mint()) has .key, .supply, .decimals, .mintAuthority, .freezeAuthority
  // clock (from bs.clock()) has .unixTimestamp, .slot, .epoch
}
```

When accounts are constraints like `bs.mut(Counter)`, you get the full account data:

```ts
run: ({ counter }) => {
  // counter.count — bigint
  // counter.authority — string
  // counter.isActive — boolean
}
```

Account values from `bs.init()` and `bs.mut()` also include a `key` field with the account's address:

```ts
run: ({ counter }) => {
  const address = counter.key  // string — the account's on-chain address
}
```

## What is not supported

Better-sol rejects anything not listed above. Each rejection comes with a specific error message and a suggestion for what to use instead. Here are the most common unsupported patterns:

| Pattern | What to use instead |
|---|---|
| `while` / `do-while` | A bounded `for` loop |
| `for...of` / `for...in` | A bounded `for` loop with index access |
| `switch` / `case` | Explicit `if/else` branches |
| `try` / `catch` / `finally` | `ctx.require()` for validation |
| `throw` | `ctx.require(condition, "ErrorName")` |
| `await` | Move async work to the client side |
| `Math.*` functions | Arithmetic operators or write the logic directly |
| Template strings (`` ` ``) | String literals in `ctx.log()` with `{}` placeholders |
| Object spread (`{...obj}`) | Write each field explicitly |
| Destructuring assignments | Declare each variable explicitly |
| Nested functions or closures | Inline the logic directly |
| `return` without `returns` in config | Add `returns: bs.u64()` (or the appropriate type) to the instruction config |

Better-sol is intentionally conservative with what it accepts. It only supports patterns it can reliably convert to correct on-chain logic. When something is not supported, there is usually a supported alternative that achieves the same result.
