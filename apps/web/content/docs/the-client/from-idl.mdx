---
title: Importing from an IDL
description: Three ways to use an external Solana program in your Better Sol project.
---

Not every program you interact with is one you wrote. When you need to call instructions, fetch accounts, or parse errors from an external program, you need its IDL: a JSON description of the program's interface.

Better Sol offers three ways to do this, depending on your needs.

## Which approach should you use?

| Approach | Type safety | When to use |
|---|---|---|
| **Generate a typed program** | Full autocomplete on instruction names, account names, errors, args | You know the program at build time. Recommended. |
| **Load with `fromIdl()`** | Instruction and account names are `string`, no autocomplete | You need runtime flexibility, or cannot run a CLI step. |
| **Write by hand** | Full control, same as writing your own program | The IDL is incomplete or you need custom behavior. |

---

## Generate a typed program

The `generate idl` command reads an IDL and produces a `.ts` file that uses the same `bs.account()` and `bs.program()` APIs you would use for your own programs. Because it outputs real TypeScript, you get full autocomplete and type checking.

### From an on-chain program

Pass a program address. Better Sol fetches the IDL from the chain:

```bash
npx @better-sol/cli generate idl 12b3t1cNiAUoYLiWFEnFa4w6qYxVAiqCWU7KZuzLPYtH
```

This connects to mainnet, fetches the on-chain IDL, and writes a TypeScript file:

```
generated/staking.ts
```

By default it targets mainnet. Use `--cluster` for other networks:

```bash
npx @better-sol/cli generate idl Fg6PaFpoGXkYsidMpWTK6W2BeZ7FEfcYkg476zPFsLnS --cluster devnet
```

### From a local IDL file

If you have an IDL JSON file on disk (downloaded from an explorer, provided by a team, etc.):

```bash
npx @better-sol/cli generate idl ./staking-idl.json
```

Better Sol detects whether the argument is a program address or a file path automatically.

### Options

| Flag | Default | Description |
|---|---|---|
| `--out <path>` | `generated/<name>.ts` | Output file path |
| `--name <name>` | Derived from IDL metadata | Override the exported variable name |
| `--cluster <cluster>` | `mainnet` | Cluster for on-chain fetch (`mainnet`, `devnet`, `testnet`, `localnet`) |

### What the output looks like

The generated file is a normal Better Sol program definition. Here is a simplified excerpt from the staking program:

```ts
// Generated by better-sol from on-chain:12b3t1cNiAUoYLiWFEnFa4w6qYxVAiqCWU7KZuzLPYtH. Do not edit.
import { bs } from "better-sol/program"

const StakePool = bs.account({
  total_staked: bs.u64(),
  rewards_per_token_stored: bs.u128(),
  pending_rewards: bs.u64(),
  initialized: bs.bool(),
  bump: bs.u8(),
})

const UserStake = bs.account({
  owner: bs.pubkey(),
  staked_balance: bs.u64(),
  bump: bs.u8(),
})

export const staking = bs.program({
  name: "staking",
  address: "12b3t1cNiAUoYLiWFEnFa4w6qYxVAiqCWU7KZuzLPYtH",
  accounts: { StakePool, UserStake },
  errors: {
    ZeroAmount: "Amount must be greater than zero",
    Unauthorized: "Unauthorized: signer does not own this stake account",
  },
  events: {
    Staked: {
      user: bs.pubkey(),
      amount: bs.u64(),
      new_balance: bs.u64(),
    },
  },
}, ix => ({
  claim: ix({
    accounts: {
      user: bs.signer(),
      stake_pool: bs.mut(bs.account({})),
      user_stake: bs.mut(bs.account({})),
    },
    run: ({ user, stake_pool, user_stake }, ctx) => {},
  }),
  stake: ix({
    accounts: {
      user: bs.signer(),
      stake_pool: bs.mut(bs.account({})),
      user_stake: bs.mut(bs.account({})),
    },
    args: { amount: bs.u64() },
    run: ({ user, stake_pool, user_stake }, { amount }, ctx) => {},
  }),
}))
```

The generator maps every IDL concept to Better Sol APIs:

- **Accounts** with field definitions become `bs.account()` with typed fields
- **Instructions** become `ix()` calls with the correct account constraints (`bs.signer()` for signers, `bs.mut()` for writable accounts)
- **Errors** become a `Record<string, string>`
- **Events** with field definitions get their fields mapped to type tokens

Accounts that appear in instructions but do not have field definitions in the IDL (like `system_program`, `token_program`) get `bs.account({})` as a placeholder. This is enough for the client to work, even without knowing the internal layout.

### Using it in your app

Import and register the generated program like any other:

```ts
import { betterSol } from "better-sol"
import { staking } from "./generated/staking"

const sol = await betterSol({
  cluster: "mainnet",
  programs: { staking },
})

await sol.staking.claim()
await sol.staking.stake({ amount: 100n })

const pool = await sol.staking.accounts.StakePool.fetch(addr)

sol.staking.parseErrors(logs)
sol.staking.parseEvents(logs)
```

All client features work. See [The Client](/docs/the-client/connecting) for the full API.

### Why generated files go in `generated/`

The `deploy` command discovers programs to compile and deploy from `programs/**/*.ts`. Generated IDL programs are client-side definitions with no on-chain logic to compile. Keeping them in `generated/` prevents them from being picked up by deploy.

## Load at runtime with `fromIdl()`

If you cannot run a CLI step (for example, your app loads program IDs from a database or config), use `fromIdl()` to create a program definition from an IDL JSON object at runtime:

```ts
import { betterSol, fromIdl } from "better-sol"

const idl = await fetch("/staking-idl.json").then(r => r.json())

const staking = fromIdl(idl)

const sol = await betterSol({
  cluster: "mainnet",
  programs: { staking },
})

await sol.staking.claim()
await sol.staking.stake({ amount: 100n })
```

This works, but instruction names, account names, and error names are `string`. You get no autocomplete. The client still resolves the right discriminators and encodes args correctly at runtime, but TypeScript cannot check that `"claim"` is a real instruction or that `100n` is the right type for `amount`.

You can also load an IDL object inline:

```ts
const staking = fromIdl({
  address: "12b3t1cNiAUoYLiWFEnFa4w6qYxVAiqCWU7KZuzLPYtH",
  metadata: { name: "staking", version: "0.1.0", spec: "0.1.0" },
  instructions: [
    {
      name: "stake",
      accounts: [
        { name: "user", writable: true, signer: true },
        { name: "stake_pool", writable: true },
      ],
      args: [{ name: "amount", type: "u64" }],
    },
  ],
  accounts: [
    { name: "StakePool", discriminator: [121, 34, 206, 21, 79, 127, 255, 28] },
  ],
  types: [
    {
      name: "StakePool",
      type: {
        kind: "struct",
        fields: [
          { name: "total_staked", type: "u64" },
          { name: "initialized", type: "bool" },
        ],
      },
    },
  ],
})
```

### When `fromIdl()` gives you typed names

There is one case where `fromIdl()` provides literal instruction and account names. If you pass the IDL as a `const` assertion, TypeScript narrows the string literals:

```ts
import type { AnchorIdl } from "better-sol"

const idl = {
  address: "Ctr11111111111111111111111111111111111111",
  metadata: { name: "counter", version: "1.0.0", spec: "0.1.0" },
  instructions: [
    {
      name: "increment",
      accounts: [{ name: "counter", writable: true }],
      args: [{ name: "amount", type: "u64" as const }],
    },
  ],
  accounts: [{ name: "Counter", discriminator: [0, 1, 2, 3] }],
  types: [
    {
      name: "Counter",
      type: { kind: "struct" as const, fields: [{ name: "count", type: "u64" as const }] },
    },
  ],
} as const satisfies AnchorIdl

const counter = fromIdl(idl)

// TypeScript knows these names:
counter.instructions.increment
counter.accounts.Counter
counter.errors
```

This only works when the IDL is statically known at compile time. If you load it from a file at runtime (with `JSON.parse`, `fetch`, etc.), the string types widen to `string` and you lose the literal names.

## Write by hand

The most flexible option. You construct the program definition yourself using the same `bs.program()` API you would use for your own programs. This is useful when the IDL is incomplete, wrong, or you want to add things the IDL does not describe (like extra events, custom error messages, or derived account layouts).

```ts
import { bs } from "better-sol/program"

const StakePool = bs.account({
  total_staked: bs.u64(),
  rewards_per_token_stored: bs.u128(),
  initialized: bs.bool(),
  bump: bs.u8(),
})

export const staking = bs.program({
  name: "staking",
  address: "12b3t1cNiAUoYLiWFEnFa4w6qYxVAiqCWU7KZuzLPYtH",
  accounts: { StakePool },
  errors: {
    ZeroAmount: "Amount must be greater than zero",
    Unauthorized: "Not the stake account owner",
  },
}, ix => ({
  stake: ix({
    accounts: {
      user: bs.signer(),
      stake_pool: bs.mut(StakePool),
    },
    args: { amount: bs.u64() },
    run: ({ user, stake_pool }, { amount }, ctx) => {},
  }),
}))
```

You have full control. Define only the accounts and instructions you actually use. Skip the rest. Add derived fields or custom type mappings. The client treats this exactly like any other program definition.

This is the same pattern covered in [Program Config](/docs/defining-programs/program-config). The only difference is intent: you are describing someone else's program, not writing your own.
